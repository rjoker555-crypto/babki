# Чтение существующего договора объекта

Проблема: агент нашёл договор «Гостиница кузня», но сообщал об отсутствии содержимого. В Supabase документ `4ed26221-620f-4205-899b-3879daed3ad0` является версией 1 DOCX, 33364 байта, в private project-documents. До исправления get_project_context/search_company_documents возвращали только title/type/file_name/version, а инструмента чтения не было. Возможность просмотра в браузере не означает передачу файла модели.

Добавлен read_company_document в main-agent v8; runtime instructions 1.2.0. DOCX извлекается на сервере из основного текста, колонтитулов и сносок; ссылки имеют номер абзаца. Удалённые правки не включаются, автоматическая нумерация отмечается как ограничение, изображения Word требуют PDF. TXT читается как UTF-8. PDF разбивается по четыре страницы и передаётся Responses input_file; результат отмечает переданные исходные страницы, не притворяется готовым OCR.

Инструмент получает UUID документа и offset. Хранилище/path берутся только из серверной записи, произвольный URL не принимается. Повторно проверяются активность профиля, закрытый директорский allowlist и назначение объекта. Договор не раскрывается прорабу; прорабу доступны только назначенные документы типа project. Чтение не меняет данные и не требует подтверждения.

Лимиты: до 8 MiB на документ, до четырёх документов/16 MiB за ответ, до 500000 символов извлечённого текста, окно 14000 символов с уменьшением при JSON-экранировании; PDF до 200 страниц, чтение частями. ZIP ограничен размером распаковки, числом частей/entries, проверяет CRC и rejects XML entities. Результат содержит filename/version/updated_at/SHA256, покрытие и next_offset. Кэш существует только внутри одного ответа; изменение метаданных версии прерывает последовательное чтение. Полный schema.ts не требуется для чтения документа.

Цикл агента увеличен до восьми шагов в пределах прежних времени/токенов и общих квот. Инструкции требуют дочитать next_offset, явно отмечать неполноту и не просить повторно прислать доступный документ. Старые инструменты поиска остаются поиском метаданных. Для PDF файл добавляется непосредственно в следующий запрос модели, bytes/credentials не попадают в tool JSON или клиентский ответ.

Проверки:

- agent-documents.test.cjs: настоящий ZIP/DEFLATE DOCX, пункты, entities, сноски, исключение удалённых правок, source/версия/SHA256, большие тексты и кэш, реальные PDF-фрагменты, отказ неактивному/неподключённому директору/чужому прорабу, неподдерживаемый DOC/повреждение/нет файла/path traversal.
- agent-document-flow.test.cjs: вызовы контекста → юридический модуль → чтение DOCX → следующий фактический OpenAI payload содержит текст пункта. Провайдер в тесте контролируемый, не оплачиваемый.
- Старые agent.test.cjs и проверка поточного размера запроса проходят.
- Supabase deploy подтвердил ACTIVE main-agent v8 с verify_jwt=true.

Реальный файл по приватному Storage ещё не скачан в ходе проверки через пользовательскую сессию; реальный платный анализ именно этого договора не запускался. Причина отсутствия инструментов установлена по реальному документу и коду, а интеграция чтения проверена на действительном DOCX-формате. Для пользовательской проверки достаточно повторить вопрос в существующем чате. Ничего загружать заново и менять GitHub для этого исправления не требуется. Авторизация, бизнес-данные и ранее подготовленная миграция прав не изменялись.

Документация PDF file inputs: https://developers.openai.com/api/docs/guides/file-inputs
