# Изменение прежних прав — подготовка для согласования

Этот переход не применён. ТЗ разрешает безопасные добавления, но требует согласования изменений существующих прав. Новые RPC уже ограничены самостоятельно; исправление старых прямых записей затрагивает действующие пользовательские сценарии.

## Подтверждённые проблемы

- `profiles_non_foreman_all` + UPDATE/INSERT/DELETE grants разрешают активным директору, финансисту и бухгалтеру менять профили, включая роль и активность. Простой `profiles.role='director'` поэтому не является надёжным новым разрешением. Закрытый `agent_director_access` для новых глобальных команд исключает этот обход.
- `project_work_tasks_all`, `project_work_progress_all` и `work_volume_submissions_access` разрешают операции всем перечисленным активным ролям без проверки объекта/автора. `created_by` может быть подставлен прямой записью. Новое доказательство обязательства поэтому дополнительно требует неизменяемую квитанцию RPC.
- `foreman_projects` возвращает производственные поля всех объектов, а не назначенные объекты. Существующая ожидаемая область чтения отличается от строгого нового RPC.

## Конкретный предлагаемый переход

1. Снять изменения id/role/is_active у финансовых ролей; управление доступом оставить доверенному активному директору из server-only allowlist. Собственный full_name разрешить отдельно. Новые права не выводить из user_metadata.
2. Перед заменой широких политик сохранить точные pg_get_* определения и grants. Подготовить ролевые SQL-сценарии под authenticated, включая подмену роли/автора, смену объекта и неактивный аккаунт.
3. Предметную запись подачи, связанных позиций и фактов разрешать только через транзакционный RPC. До отзыва прямых записей перевести также ручной факт, завершение работы и оставшиеся UI-редакторы на предметные команды: сейчас они всё ещё используют старые записи, поэтому немедленный отзыв сломает эти сценарии.
4. После создания команды объекта ограничить SELECT прораба назначенными производственными объектами; доступ финансовых ролей к организации сохранить согласно согласованной матрице. Изменить foreman_projects и фильтрацию локального клиента согласованно, проверить повторный вход и переключение пользователей.
5. Задачи агента не должны давать новых прав на исходные документы/финансы. Прораб получает только свои задания и разрешённые производственные сведения. Сохранять основание назначения отдельно от произвольной рекомендации модели.

## Критерии перед применением

Работают ручные факты, редактирование и удаление подач, завершение работы, назначение команды и пользовательская карточка. Бухгалтер не может повысить роль или активировать пользователя. Прораб другого объекта не может читать/писать его факты. Обход прямым REST/RPC не расширяет эти права. Снимок прежних политик позволяет вернуть приложение без потери данных.

Полный SQL перехода будет сформирован после реализации оставшихся предметных команд и согласования области команды. Пока предложенный переход является конкретной последовательностью работ, а не готовой миграцией и не утверждением устранённой уязвимости.
