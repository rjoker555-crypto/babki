Дополнительные замечания: project-documents закрыт, но не имеет bucket size/MIME ограничения; manager/director имеют доступ ко всему bucket согласно нынешним политикам. Конкретные лимиты старых документов требуют проверки существующих форматов. Лимит агентских файлов 100/100 MiB проверяется приложением, параллельные разные загрузки могут соревноваться: это риск Storage расходов авторизованным пользователем, не анонимная выдача документов. Подготовленные ограничения объектов не заменяют будущую полную матрицу полей и действий сотрудников. Внешние библиотеки frontend загружаются из CDN; Supabase-js использует плавающую версию @2 и нет SRI. Компрометация поставщика JavaScript может украсть сессию; отдельное закрепление/проверка поставки предстоит.

## 4. Storage, RPC и prompt injection

project-documents и agent-files — private buckets. Анонимных политик public/storage нет. Для agent-files клиентских Storage policies нет: доступ через server endpoint проверяет активность, владельца либо привязку к объекту и назначение/доверенный директорский доступ. Владелец файла может читать свой исходник. Signed URL этого endpoint действует 60 секунд; старый UI project-documents выдаёт до 600 секунд, КП — 300. Любой получивший сам signed URL может использовать его до истечения срока; ссылку следует считать временным разрешением, не публиковать.

SECURITY DEFINER helper-функции старого приложения возвращают только проверку роли или ограниченную прорабскую карточку, но последняя имеет ошибку области доступа. Новые привилегированные RPC недоступны anon/authenticated; user-facing volume RPC проверяют uid/активность/объект. Агент не принимает SQL. Есть строгий каталог предметных tools; старый директорский CRUD остаётся совместимым allowlist с проверкой имён таблиц/полей, валидацией и конкретным подтверждением. Универсальным SQL-инструментом он не является.

Авторизация определяется сервером. Текст документа не меняет allowlist, uid, RLS или подтверждение. Worker разбора не имеет инструментов записи предметных данных. Точное отдельное сообщение владельца плана в том же чате разрешает запись; подготовка плана ничего не импортирует. Ошибка модели не считается доказательством выполнения. Prompt injection может ухудшить смысл черновика, но не должно предоставлять новые права; абсолютную устойчивость качества ответов не обещаем.

agent-worker имеет verify_jwt=false для Cron, но до любой работы проверяет отдельный 64-hex токен сервисным RPC; без него HTTP 401. Основной чат/голос/файлы имеют verify_jwt=true и повторно проверяют Auth user + активный профиль. [Официальная документация защиты Edge Functions](https://supabase.com/docs/guides/functions/auth).

Особенность управляемого pg_net: SQL grants на queue/response от PUBLIC разрешены владельцем supabase_admin. Попытка revoke через обычный postgres не изменила ACL; тест остановил и откатил первую миграцию. Код затем применён без неподтверждённого изменения этих grants. Схема net не exposed через Data API: реальный Accept-Profile: net получил 406. Токен worker не выводился. Это дополнительная область защиты для проверки через владельца инфраструктуры, а не обнаруженный публичный REST-доступ к токену. Не следует открывать net в Data API. Cron SQL вызывает закрытую функцию и не содержит значение токена.

## 7. Что требуется от владельца

1. Согласовать `security-role-hardening.PROPOSED.sql`: ограничение изменения полномочий профилей доверенным директором, границы объектов для прораба, RPC и видимости журналов. Это сужает существующие права, данные не удаляет. Если объект не имеет responsible_user_id, прораб его больше не увидит; назначение должен выполнить директор. Более полная матрица управления работами/общими каталогами остаётся отдельным этапом.
2. Опубликовать локальный index.html с изоляцией документов и предыдущие frontend файлы chat.js/volumes.js/obligations.js. Push/публикация мной не выполнялись и требуют отдельного разрешения. Актуальный GitHub main пока содержит только index.html/chat.js/manifest.json.
3. В Supabase Auth отключить самостоятельную регистрацию, если используется только приглашение сотрудников. Это полезное усиление; без активного профиля регистрация уже не даёт доступ. Действующих пользователей не отключать. Настройки MFA/сроков JWT/всех identity providers через имеющиеся инструменты полностью не проверены.

Нет доказанной утечки, требующей обязательной ротации. Не требуется покупать дополнительные платные сервисы. GitHub может содержать публичный исходный код без server credentials, однако смена видимости репозитория не устранит действующие серверные обходы прав. До согласования/применения ограничения прав и публикации предпросмотра общий вердикт остаётся красным.
