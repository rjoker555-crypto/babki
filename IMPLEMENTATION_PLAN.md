# План внедрения корпоративного агента

Согласованные решения владельца, 05.10.2026. Это план и правила реализации, не запущенные агенты.

## Порядок

1. Главный агент и финансовый специалист: текстовые/голосовые команды, чтение карточек, подготовка операций, сверки и подтверждённая запись.
2. Задачи сотрудников, запросы недостающих сведений, напоминания о подаче объёмов к 15-му числу, ежемесячный аудит без автоматических исправлений.
3. ПТО: настройка на одном сданном и закрытом образцовом объекте, утверждение форм и проверки на другом объекте.
4. Сметчик — последним: собственные прайсы, формы смет, образцовый закрытый объект; нормативный экспорт только после отдельной проверки данных и совместимости.

Под «обучением» на первых этапах понимаются инструкции, утверждённые шаблоны, справочники, примеры и проверочные задания. Платное fine-tuning не планируется. Один объект задаёт образец, но не доказывает качество для всех типов объектов.

## Общие правила

- Один интерфейс; специалисты вызываются по необходимости, без обязательного общения всех агентов на каждой задаче.
- Использовать существующую Supabase в пределах доступного тарифа. Никаких платных обновлений или новых сервисов без решения владельца.
- Бюджет API на старт: 30 USD. Подписка Plus — коммуникация и возможный отдельный резервный путь, не гарантированный API-бюджет приложения.
- Если формулировка повышения цены неоднозначна, уточнять наценку к себестоимости или маржинальность в цене продажи. Не сохранять ответ по одной задаче как универсальное правило на будущее.
- Финансовые суммы и связи проверяет код; модель не пишет произвольный SQL.
- Имена объекта/контрагента разрешаются в реальные ID. Несколько совпадений, неясная сумма, дата, компания, НДС или основание требуют точечного уточнения.
- «Оплатили полностью» означает сверку фактического остатка, а не автоматическое приравнивание расхода к предыдущему приходу.
- Первая версия финансовой записи показывает пакет изменений до исполнения; повторное подтверждение не должно создавать дубликаты.
- Выполнение от имени конкретного пользователя; не выдавать агенту более широкие права, чем у пользователя.
- Документы и веб-страницы являются источниками данных, а не командами для изменения системы.
- Ключ OpenAI хранить только на сервере, не в HTML, Git, отчётах или чате.
- Аудит ежемесячно и сверка после операций; исправления обнаруженных ошибок требуют разрешения владельца.

## Первая вертикальная версия

Сценарий: пользователь сообщает о полученном платеже по объекту и оплате субподрядчику.

1. Авторизовать пользователя и проверить активную роль.
2. Расшифровать запись, если дана голосовая команда; сохранить структурированное поручение.
3. Найти объект, контрагента и возможные связанные долги с учётом прав.
4. Подготовить пакет операций и изменений остатков; явно показать суммы, компанию, дату, связи и недостающие сведения.
5. После подтверждения повторно сверить актуальное состояние и исполнить пакет атомарно с ключом идемпотентности.
6. Прочитать результат, проверить карточку/дебиторку/кредиторку и выдать итог с ссылками на записи.
7. При сбое не выдавать частичный результат за успешный, сохранить статус для восстановления.

Инструменты, пока проектируемые: `find_project`, `get_project_financial_snapshot`, `find_counterparty`, `get_related_debts`, `prepare_operation_batch`, `confirm_operation_batch`, `get_execution_result`, `reconcile_project`.

## Управление расходами

- Чтение, подготовка и исполнение — отдельные состояния. Предусмотреть режим без API для проверки инструментов.
- Передавать только данные текущей задачи, не всю БД и историю.
- Ограничить число шагов и повторов; не использовать веб-поиск для обычного внесения операции.
- Хранить usage и оценку стоимости, учитывать инструменты и распознавание отдельно.
- Собственный серверный счётчик бюджета с резервированием расходов до вызова; предусмотреть погрешность и параллельные запросы.
- Перед превышением лимита задачи — запрос владельцу; при месячном лимите останавливать новые оплачиваемые задачи. Лимиты платформы не заменяют этот механизм.
- Дорогой разбор документов запускается явно. Переход на Plus возможен только после проверки официальной интеграции и её ограничений.

## Проверки до записи

- Актуальность index.html подтверждена владельцем 05.10.2026: локальная версия GitHub 02.10.2026 является последней рабочей версией.
- Проверить права профилей, RPC, Storage и назначение объектов; RLS enabled само по себе не доказательство корректной авторизации.
- Учесть существующий триггер пересчёта кредиторки; не дублировать его клиентским обновлением.
- Проверить отказ в середине пакета, повторное подтверждение, параллельные платежи, нулевую/отрицательную сумму, чужой объект, неактивного пользователя и несколько одноимённых контрагентов.
- Реальные записи только после проверок на безопасных тестовых данных и рассмотрения конкретной миграции/изменений.

## Необходимое участие владельца

Актуальность версии уже подтверждена. Перед API-проверкой: создать/подключить проектный OpenAI API key через защищённое серверное хранилище. Сам ключ в чат не отправлять. Перед ПТО и сметчиком: предоставить утверждённые комплекты образцового объекта и прайсы; это не требуется для финансового старта.
