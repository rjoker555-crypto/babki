# Первичный read-only снимок Supabase

Дата: 05.10.2026. Проект совпадает с URL в index.html: `tkoxgvftneoereukiomr`. Подключённый Supabase-инструмент уже имеет доступ. Выполнены только чтение метаданных, списка миграций/Edge Functions и security advisors. Рабочие финансовые записи, документы и содержимое пользовательских профилей не выгружались. Схема и данные не изменялись. Ключи не запрашивались.

## Подтверждённые факты

- Проект ACTIVE_HEALTHY, PostgreSQL 17.
- В public 35 таблиц; RLS включена на всех 35.
- 18 зарегистрированных миграций; Edge Functions пока нет.
- Помимо 32 таблиц, использованных клиентом, есть `audit_log`, `sync_records`, `project_subcontractors`.
- Прочитаны определения девяти public-функций, политики public/storage, grants и два прикладных триггера.
- На operations действует `trg_sync_payable_paid_amount`: INSERT/UPDATE/DELETE для статьи «Погашение кредиторки» вызывают серверный пересчёт paid_amount. Это уточняет A02/A08 исходного AUDIT.md: для кредиторки серверный пересчёт существует, но пакет действий целиком транзакционным от этого не становится.

## Вопросы до допуска агента к записи

1. `profiles_non_foreman_all` разрешает ALL по предикату `is_non_foreman_active()`, без ограничения целевой строки. Функция проверяет активную роль director/finance/accountant. Соответствующие grants включают UPDATE; в прочитанных public-триггерах запрета изменения role нет. По определениям политики финансовые роли могут менять профили, в том числе роль. Это серьёзное расширение прав; фактический запрос изменения специально не выполнялся. Нужно определить разрешённую матрицу и проверить её тестами перед корректировкой.
2. `audit_log` также имеет ALL по `is_non_foreman_active()`: такой журнал нельзя считать неизменяемым свидетельством действий без дополнительной защиты.
3. Производственные политики проверяют роль, но во многих случаях не ограничивают строки назначенным объектом. `foreman_projects()` возвращает все проекты для активных foreman/manager, `foreman_subcontractors()` — всех субподрядчиков для foreman. Это может быть намеренной бизнес-логикой; до внедрения агента нужно явно зафиксировать область доступа.
4. Несколько таблиц имеют широкие grants anon/authenticated. Наличие grants не доказывает доступ к строкам благодаря RLS; необходим анализ совместного действия grants/policies, включая права вне обычного CRUD.
5. Security advisors дают предупреждения о шести SECURITY DEFINER функциях, доступных authenticated, и об отключённой защите скомпрометированных паролей. Сам SECURITY DEFINER не доказательство ошибки: нужно учитывать проверки внутри функции. Автоматические исправления не выполнялись.

Рекомендации Supabase по предупреждениям: [SECURITY DEFINER](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable), [защита паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection).
