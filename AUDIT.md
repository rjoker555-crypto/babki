# Аудит проекта «Финансы компании»

Дата: 05.10.2026 (Asia/Krasnoyarsk). Режим: read-only для существующего проекта; создан только этот отчёт.

## 1. Итог и границы достоверности

Приложение — статический клиент финансового и производственного учёта с прямым доступом к Supabase. Это функциональная база для корпоративного помощника, но готовность к безопасному агенту с правом записи не подтверждена. Сначала необходимы проверка серверной авторизации, атомарность финансовых действий и воспроизводимая схема БД. Реализация LLM, серверного агентного API, поиска по документам и журналирования действий агента в доступных файлах не обнаружена.

Проверены оба исходных файла, структура и состояние Git, клиентские потоки Auth/CRUD/Realtime/Storage, расчёты и отчёты, роли, документы, производственный учёт, зависимости, статическая корректность. Серверная схема, RLS, RPC, Storage policies, индексы, ограничения, триггеры, инфраструктура, резервные копии и реальные данные не предоставлены. Отсутствие этих материалов в репозитории не означает отсутствие защиты на сервере.

Приложение не запускалось: `loadAll()` вызывает `migrateLegacyPlannedCost()` и способно записывать данные уже при загрузке. Не выполнялись вход, запросы к рабочей БД, загрузки файлов, миграции, установка пакетов, коммиты или изменения исходников. Использованы чтение файлов, Git-команды чтения и анализ JavaScript в памяти без исполнения приложения. Просмотрена официальная документация Supabase для проверки принципов авторизации.

## 3. Архитектура и возможности

Поток: браузер → Supabase Auth → профиль и роль → PostgREST/RPC + Storage + Realtime → глобальные массивы → вычисления и HTML. Отдельного серверного слоя в репозитории нет. Подключение задано в `index.html:1498–1512`; сессия сохраняется и автоматически обновляется. Ключ имеет тип `sb_publishable_`: его наличие во frontend само по себе не утечка серверного секрета. Значение в отчёте не повторяется.

Роли (`index.html:2073`): директор, финансы, бухгалтер, прораб, управляющий. Для управляющего и прораба есть отдельная загрузка и RPC `foreman_projects`, `foreman_subcontractors`; добавление субподрядчика прорабом использует `foreman_add_subcontractor`. Скрытие элементов интерфейса и клиентские проверки ролей не заменяют серверную авторизацию.

Основные области:

- Дашборд, денежные операции, дебиторка, кредиторка, кредиторы, календарь платежей и события.
- Объекты, план/факт доходов и затрат, субподрядчики, материалы, прочие расходы, организационные расходы и сотрудники.
- Управленческий налоговый регистр, история расчёта НДС, отчёты и выписки.
- ПТО, документы и контакты заказчика, договоры и дополнительные соглашения, версии файлов, история изменения цены.
- Ход работ: справочники, разделы, шаблоны составов, материалы, факт выполнения, подачи объёмов, задачи, календарь и диаграмма сроков.
- Коммерческие предложения: статусы, источники, причины проигрыша, прикреплённые письма и статистика.

Внешние зависимости (`index.html:1491–1495`): Supabase JS `@2` (плавающая версия), html2pdf.js 0.10.1, mammoth 1.8.0, SheetJS 0.20.3. Загружаются с CDN; SRI в тегах не указан. Статус известных уязвимостей этих версий не проверялся, безопасными они не объявляются.

## 7. План корпоративного ИИ-агента

### Рекомендуемая граница

Браузер → сервер агента → проверка пользователя и прав → разрешённые предметные инструменты → Supabase. Ключ провайдера модели хранить на сервере. Не передавать модели service_role и не давать произвольный SQL/произвольный CRUD. Полномочия инструмента определяются сервером по пользователю, объекту и действию, а не текстом модели.

### Первый этап: помощник только для чтения

1. Подтвердить RLS/RPC и полноту серверных агрегатов. Версионировать схему и правила финансовых расчётов.
2. Реализовать ограниченные инструменты сводки объекта, долгов, платежей, сроков ПТО, хода работ и задач. Ответ включает период, момент актуальности и ссылки на исходные сущности.
3. Суммы получать из проверяемых предметных расчётов; модель объясняет результат, а не выполняет бухгалтерию самостоятельно.
4. Для поиска по документам: безопасное извлечение, версии, ссылки на документ/страницу, фильтрация прав до поиска и после него. Текст документов считать данными, не инструкциями агенту.
5. При неполной выборке, отказе источника или устаревшем снимке явно сообщать об ограничении вместо достоверной на вид суммы.

### Второй этап: контролируемые действия

После устранения A02/A03/A05/A06/A08 вводить предметные команды, например создать задачу или подготовить операцию. Для финансовых изменений показывать конкретный предварительный результат и запрашивать подтверждение; использовать транзакцию, идемпотентный ключ и журнал «кто/что/когда/основание/результат». Разделить подготовку и исполнение, запретить удаление/изменение через текст документа. Не выводить скрытые финансовые поля производственным ролям.

### Критерии готовности

- Негативные тесты по каждой роли: финансы, чужой объект, документы, изменение роли, прямой вызов RPC и инструмента агента.
- Проверки финансовых инвариантов при повторном запросе, двух одновременных пользователях и отказе посередине действия.
- Проверки отсутствия записи при чтении; полноты результатов на объёме выше серверного лимита; даты около полуночи.
- Набор агентных сценариев с эталонными ответами, доказательствами источников, отказом на запрещённое действие и prompt injection в документах.
- Метрики ошибок, времени, стоимости и полноты ответа; журнал действий без паролей, токенов и избыточных персональных данных.

## 9. Источники проверки принципов Supabase

- [Row Level Security](https://supabase.com/docs/guides/database/postgres/row-level-security): grants и политики определяют доступ на стороне БД; frontend не заменяет их.
- [API keys](https://supabase.com/docs/guides/getting-started/api-keys): publishable key предназначен для публичного клиента; привилегированные ключи должны оставаться на сервере.
