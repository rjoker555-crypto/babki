# Личный чат — первая версия

В index.html добавлена вкладка «ИИ-чат», доступная всем существующим ролям. chat.js хранит переписку в Supabase, показывает события отдельными сообщениями, очищает состояние при выходе/смене пользователя и отбрасывает устаревшие ответы. Текст выводится через textContent. Подключена серверная функция main-agent для текстовых ответов. Голос, предметные операции и вложения — следующий этап.

В существующую Supabase применена добавочная миграция `private_chat_and_activity_feed`; SQL сохранён в chat-schema.sql. Повторно этот SQL применять нельзя без адаптации, поскольку таблицы и триггеры уже созданы.

- agent_chat_messages: SELECT только owner_id=auth.uid() для активного пользователя. INSERT только в свой чат и только kind=user. Другие роли приложения, включая директора, не получают доступ к чужой переписке. Администратор БД/service_role технически имеет административный доступ.
- agent_activity_events: клиент имеет только SELECT, финансовые события доступны director/finance/accountant, производственные — также manager/foreman. Это соответствует текущему общему доступу производственных ролей к объектам; ограничения по назначенным объектам в исходной системе пока нет.
- Приватная триггерная функция записывает автора, объект, тип сущности и действие без содержимого переписки, сумм и полных old/new снимков. Пользователь не может подделать событие через клиентский INSERT.
- Отслеживаются карточки объектов, субподрядчики, операции и долги, затраты, документы/ПТО, работы/факт/разделы/задачи и подачи объёмов. Детальные строки материалов работ, контакты, шаблоны, КП и организационные расходы пока не покрыты.
- Старые события не восстанавливаются. В чате показаны последние 100 доступных событий и страницы личных сообщений по 50. Открытый чат обновляется каждые 30 секунд, также при открытии вкладки и вручную.
- При записи через service_role без пользовательского JWT автор отображается как «Системный процесс». Будущий сервер агента должен сохранять достоверного инициатора через предметные команды; не подставлять пользовательское имя из текста модели.
- События являются системной лентой. Отправка сообщения отдельно вызывает main-agent и OpenAI Responses API; обновление ленты не расходует API.

## Директорский режим с подтверждением

Пользователь проверил настоящий ответ через приложение — OpenAI подключён. По последующему запросу добавлен директорский режим: чтение (до 30 записей по равенству фильтров), добавление, изменение и удаление записей 32 предметных таблиц, плюс чтение profiles. Схема и разрешённые поля сохранены в supabase/functions/main-agent/schema.ts. Ключи, схемы БД, чужие чаты, системные журналы, управление аккаунтами и файлы Storage этим механизмом не доступны. Создание/чтение файлов и интернет ещё не реализованы. Это доступ к предметным данным директора, а не административный доступ к Supabase.

Применена миграция director_agent_exact_approvals (director-actions.sql). agent_director_access первоначально содержит активных директоров на момент миграции. Таблица закрыта от клиентов, поэтому самостоятельное изменение role через старую широкую политику profiles не выдаёт доступ к агенту. Каждый запрос также проверяет текущие role=director и is_active. Для подключения нового директора позже требуется отдельная серверная настройка.

Модель формирует строгий JSON-план, но не исполняет его. Сервер проверяет таблицу и поля, сохраняет неизменяемое предложение и показывает реальные значения, для update — было/станет, для delete — строку. Даже чтение требует отдельного сообщения `ПОДТВЕРЖДАЮ <UUID плана>`; отмена — `ОТМЕНЯЮ <UUID плана>`. Слово «да» само по себе не считается разрешением. Срок 30 минут. Команды не вызывают OpenAI.

Серверная SQL-функция выполняется только service_role, повторно проверяет директора, владельца, точное пользовательское сообщение и срок. Блокировка предложения обеспечивает однократное выполнение. Изменения строки после показа плана блокируют update/delete. Удаление при наличии зависимых FK-записей блокируется, чтобы не каскадировать несогласованное удаление. SQL не поступает от модели: идентификаторы валидируются и экранируются, данные параметризованы. Обновления выполняются в транзакции; существующие триггеры и пересчёты остаются активны. created_by назначается сервером, автор событий берётся из проверенной личности. Обновление paid_amount напрямую заблокировано на сервере планирования; нужны операции.

Инструкция и схема увеличивают контекст; максимум ответа изменён до 2000 токенов, прежние лимиты числа запросов сохранены. Неверное предложение, ошибка ограничений БД или недоступный инструмент приводят к отказу, а не попытке обойти проверки. Сложные сценарии, требующие согласованного изменения нескольких записей или загрузки файла, пока требуют отдельных инструментов и дальнейшей проверки бизнес-логики.

Проверки: tests/agent.test.cjs — также план без исполнения, отказ другим ролям, точное подтверждение без вызова OpenAI; tests/chat.test.cjs и git diff --check — PASS. SQL с ROLLBACK: точное подтверждение, реальное обновление тестовой карточки, повтор, конфликт версии, фильтр чтения и блокировка каскадного удаления — PASS. Клиент не может создать планы, предоставить доступ или вызвать выполнение. Боевые записи не менялись. main-agent развёрнут как версия 2. Модель формирования планов ещё требует пользовательского теста; опубликованный frontend не обновлён.

## Личные разговоры, голос и отдельный протокол — текущая версия

6 октября 2026: main-agent версия 3, transcribe-voice версия 1; обе функции развёрнуты с verify_jwt=true и дополнительной серверной проверкой Auth. Эти изменения заменяют прежнее требование разрешать чтение. Директор читает предметные таблицы автоматически; сервер возвращает результат модели для содержательного ответа. На одно сообщение не более трёх обращений к модели и ограниченные выборки до 30 строк. Подтверждение по-прежнему необходимо для insert/update/delete, включая новые платежи как изменение данных. Работа с файлами объектов ещё не подключена; её разрешения не сняты.

Вкладки внутри ИИ-чата: «Чат», «История чатов», «Протокол», кнопка «Новый чат». agent_conversations хранит владельца, заголовок и время последнего сообщения. Прежняя переписка перенесена в «Первый чат» каждого владельца. Композитный FK (chat_id, owner_id) не позволяет записывать сообщение в чужой разговор; RLS закрывает переписку и список разговоров даже от других директоров. Контекст модели ограничен выбранным разговором. Подтверждать план можно только в том разговоре, где он показан. Клиент не управляет временем хранения; заголовок и last_message_at обновляет приватный триггер.

Enter отправляет и на компьютере, и через мобильное событие beforeinput/enterkeyhint=send; Shift+Enter — новая строка, IME не запускает отправку. При отправке и записи блокируются повторная отправка и смена разговора. При выходе данные очищаются, микрофон освобождается, запоздалые ответы отбрасываются. Расшифровка остаётся в поле ввода при ошибке сохранения; успешно сохранённый текст виден в истории как голосовое сообщение.

Кнопка «Голос»: MediaRecorder WebM/MP4 с лимитом 3 минуты и 3 МБ, отдельная кнопка отмены. transcribe-voice передаёт запись в OpenAI gpt-4o-mini-transcribe, получает весь текст, после чего чат отправляет его в main-agent. Суммы/названия не проходят отдельное «исправление» или пересказ. Ошибки распознавания всё же возможны; неоднозначные сведения агент должен уточнить, записи требуют подтверждения. Сервер проверяет активность и принадлежность разговора, ограничивает фактический размер входящего потока и резервирует запрос в agent_voice_runs: 20 записей в сутки UTC на пользователя, 300 в календарный месяц UTC на приложение, интервал 10 секунд и запрет повторного request_id. Аудио не сохраняется в Supabase; сохраняется полная расшифровка. Если текст длиннее 8000 символов, сервер отказывает без скрытого обрезания. Микрофон требует разрешения пользователя и поддерживаемого безопасного контекста (HTTPS/localhost; поведение file:// зависит от браузера).

Протокол отделён от переписки. agent_protocol_entries хранит инициатора, краткое поручение, запрошенные значения, выполнение/отмену; отдельная минимальная сводка поручения сохраняется и для задач, у которых ещё нет исполнителя. Это запись о приёме поручения, а не свидетельство выполнения. Полная личная переписка в общий протокол не копируется. Финансовые записи доступны финансовым ролям; автор видит собственные поручения. Изменения приложения через прямые действия пользователей тоже записываются: триггеры покрывают все 33 текущие предметные таблицы, включая организационные разделы, каталоги и шаблоны. Для прямых изменений сохраняются автор, действие, тип и UUID записи без финансового содержимого old/new. Плановые изменения и события триггеров отображаются отдельно, так что одно действие может дать несколько связанных записей. Счётчик отмечает новые доступные записи других авторов; открытая вкладка обновляется каждые 30 секунд. Это уведомление внутри приложения, без push/SMS. Удалённые или старые события до включения журнала не восстанавливаются.

Хранение: чат скрывается через 14 суток после последнего сообщения (включая ответ агента); просмотр историю не продлевает. Протокол и события скрываются через один календарный месяц от своей публикации по Asia/Krasnoyarsk, с корректным переходом концов месяцев. Приватная prune_chat_data физически очищает истёкшие записи каждый час в минуту 17 через pg_cron, даже если приложение закрыто. Технические счётчики без текста сообщений хранятся отдельно для защиты лимитов: удаление чата не позволяет сбросить квоту. Планы и их снимки удаляются через месяц. Политики сроков скрывают данные сразу, физическое удаление может отставать до часа. Это сроки прикладной базы, без управления резервными копиями платформы.

Применённые SQL: chat-history.sql (personal_threads_voice_protocol_retention), protocol-coverage.sql (complete_application_activity_protocol), calendar-retention.sql (local_calendar_protocol_retention). Старые добавочные SQL не предназначены для повторного применения.

## Исправление отсутствующего списка объектов

Пользователь подтвердил настоящий путь голос → полная расшифровка → ответ, но ответ на «Покажи мне список объектов» содержал только обещание показать список. Метаданные запроса: активная роль director, технический статус completed, 13858 входных и 91 выходной токен; в базе 8 объектов. Этот статус означает сохранённый ответ, а не проверенное выполнение поручения. Трасса чтений для старого запроса не сохранялась, поэтому точные возвращённые строки по нему ретроспективно не установлены.

Исправление: стандартный запрос списка объектов теперь распознаёт сервер после проверки пользователя и директорского доступа. Он читает актуальные названия/заказчиков/статусы/договоры и формирует сам список, без OpenAI и без разрешения на чтение. Запрос учитывается в защитной квоте обращений с нулевыми токенами. Выборка 31 строки позволяет показать до 30 и явно сообщить о продолжении. Нулевая выборка даёт явное «не найдено». Для остальных чтений сервер добавляет к ответу фактические результаты независимо от того, что написала модель. Длина ограничена с явным указанием неполного вывода. Обещание показать список без нового чтения больше не выдаётся как успешное чтение.

tests/agent.test.cjs: воспроизведение пустого обещания при выполненном чтении, обещание без чтения, список из 8 записей, пустая база, частичная выборка, отсутствие вызова OpenAI для простого списка и сохранение проверки роли — PASS. Регрессии чата и голоса также PASS. Изменение только серверное; опубликованный frontend не требуется менять для этой поправки. Новую выдачу списка с настоящей пользовательской сессией нужно проверить повторным запросом.
